## Helpers (Utils.cs)


#### CircularBuffer\<T\>

CircularBuffer\<T\> is an array of elements of type <code>T</code>, with a predefined and immutable length, whose elements are added sequentially, and you always know which element is the first one, i.e., the one which was added most remotely in the past, and the last one, i.e., the one which was just added. Since all you do is incrementing an index and, upon reaching the top of the buffer, wrapping around, updating a circular buffer is an extremely fast operation. (I was surprised to find no C# implementation of a circular buffer, so I did my own one.) So far, circular buffers are only used to store timestamps generated by the ticking of a block, which enables calculating the rate of the block as the ratio of the number of timestamps gathered so far in the buffer, and the difference between the first and last timestamp.

#### DBWriter

DBWriter is a utility to dump data to the disk in the safest possible way: following the idea of double buffering, you add things to a DBWriter and it stores them in a buffer in the memory, so there is no waiting for the disk write operation to finish. Once this buffer is exhausted, the add operation is deviated to a second buffer while the first buffer gets dumped to the disk in one single strike, asynchronously. Then vice-versa. DBWriters are used so far to dump a block’s output to the disk if required; since each output is accurately timestamped, if you switch on dumping for all blocks in your system, you will probably be able to reconstruct the whole operation of the system, instant by instant.

#### StreamManager
StreamManager is a cute smart implementation of a class able to receive without loss any data arriving from a C\# <code>Stream</code>. Many devices “stream” their data via TCP/IP, serial ports and other similar software contraptions, and each C\# class dealing with such a contraption inherits from or possesses a <code>Stream</code>. For example, a <code>TcpClient</code> has a <code>.GetStream()</code> method to this aim. Given any <code>Stream</code> then, a StreamManager will fire an event called <code>DataReceived</code> each time something is available on the stream, that is, each time the related device decides that is it time for us to get a new piece of data, or whenever the buffer associated to the StreamManager is full. (Just in case you’re wondering: this class stems from a re-implementation of the <code>SerialPort.DataReceived</code> event, which is unreliable – see the comments to the class for more details; it was then obvious to extend the class to any stream instead of only using a serial port’s stream. Note: given its unreliable, packet-lossy nature, UDP “streaming” is not based upon a <code>Stream</code>, so you cannot use a <code>StreamManager</code> with UDP. Shame.)

### Utils

#### Now
Utils.Now is possibly the most important function in the whole history of rehabilitation robotics software: it returns an *accurate timestamp* using the C\# <code>StopWatch</code> class. The <code>StopWatch</code>, once called *performance timer*, is the accurate alternative to the Windows wall-clock timing system: it is an extremely fast counter, incremented millions or billions of times a second depending on your processor and its clock frequency, which started from zero when your computer last rebooted. If you divide the value of this counter by the <code>StopWatch</code>'s frequency, you obtain the seconds elapsed since the machine was brought to life, and this timestamp is accurate to the nanosecond. This is exactly what <code>Utils.Now</code> does.<br>

#### dtmRefresh
Utils.dtmRefresh is a Windows “dispatcher timer” that you must use for all refresh operations in your code. It only appears once (static method) and contains a Tick event handler: each time you need to refresh anything, just attach your refresh call-back to this event handler. For instance, refreshing the block table is accomplished via the following simple instruction,<br><br>

```cpp
    Utils.dtmRefresh.Tick += BlockTable_refresh;
```
<br><br>
found in the block table constructor (see <code>Visualisation/BlockTable.xaml.cs</code>); this way, <code>BlockTable_refresh()</code>, further defined in the same file, will be GUI-safely called circa every 20 times a second. Besides the block table refresh routine, so far each block’s cp’s refresh routine also uses this timer, and it only attaches to the timer when the cp is visible, thus optimizing the burden of refreshing the graphical user interface.<br>

#### Print
Utils.Print is used to pretty-print all objects in iM, where by “pretty-printing” here we mean: in a Matlab-readable form. So far, trying to print <code>null</code> will result in <code>NaN</code>, printing a <code>Mathnet Vector\<double\></code> results in a comma-separated list of doubles, and all other objects are printed using the standard .ToString() method. Notice that I happily and extensively use the $ string formatting syntax, whereby $”{object}” simply results in <code>object.ToString()</code> being called. I know that having global helper functions is no really good programming, but I could not find any way to supersede the <code>Mathnet</code> built-in <code>vector.ToString()</code> method – if this had been possible, I could have used <code>$”{object}”</code> all over the place and avoid defining a pretty-printing static routine. Be my guest to try and fix this issue.<br>

## Foundational Classes (Basics.cs)

#### Scheduler
The “Scheduler” is my (Claudio’s) own solution to the ominous problem that not only Windows is no RT \(Real Time\) OS, but its timers are not at all accurate. <code>System.Windows.Timers</code> are accurate to about 15ms, meaning that you cannot reliably fire any function whatsoever more often than, say, 20 times a second, which is unacceptable for our purposes. So, <code>Scheduler</code> (a static class, there is only one instance system-wide) implements two methods <code>.Add(function,rate)</code> and <code>.Remove(function)</code> and will have <code>function()</code> fired in a reasonably accurate way <code>rate</code> times a second.

The principle behind it is ludicrously simple, almost naïve I’d say: the Scheduler is a spinning <code>while</code> loop, asynchronously firing the next function in chronological order at time $t$, then updating the function’s firing time to $t+Δt$ where $Δt$ is $1/rate$. Spinning is bad but this way there is only one centralised spinning loop – back in the days we used to have one spinning loop for each device! The Scheduler achieves a sensible accuracy, at least as far as our needs are concerned.

I am sure that the Scheduler can be improved – be my guest to try and make it better. But beware: it is one of the building bricks of iM altogether. A poor Scheduler will spoil your data collection big time and weird bugs will fly around worse than shit after it has hit a fan.<br>


#### Block
The abstract class <code>Block</code> is the foundational stone of iM. An abstract description of blocks already appears above, so here comes an explanation of its peculiarities:

-	***Evaluating the Rate.*** Each block has a circular buffer of 100 timestamps (doubles) called <code>Ticks</code> to evaluate its own rate like this: each time an output is produced, i.e., whenever <code>SendOutput(value)</code> is called, the current timestamp is added to <code>Ticks</code>; whenever <code>Rate</code> is queried, the total number of elements currently in <code>Ticks</code> is divided by the difference between the last and first timestamps in it. Why not simply evaluating the rate since the birth of the block, instead of taking the burden of memorizing the past 100 timestamps? Because a block can be started and stopped arbitrarily – actually, whether it is running depends on the blocks it is connected to – so at some point evaluating the rate over the whole course of time could become very inaccurate. Picture, e.g., the case in which a block has been running at 2kHz for one minute, then it has stopped running for two minutes, then it has run again at 2kHz for one minute: the rate since the start in this case is 1kHz, which is deadly wrong in any possible sense; using the timestamps instead, the rate is evaluated only over the “recent past”. By the way, if the block hasn’t ticked for more than one tenth of the block’s rate, we say that it is “idle” and set the related flag to true; if the Rate is less than 95% of the desired rate, we say that the block “lags” and, again, set the according flag to <code>true</code>.<br>
-	***Constructing and disposing of.*** On being constructed, each Block stores a few variables and possibly creates a DBWriter to dump its output, if the parameter <code>Path</code> is not null. On being disposed of, it removes itself from <code>Blocks.Dict</code> (see below), unsubscribes from all its input blocks and flushes its double buffer. It is very important to <code>Dispose()</code> of a block once it is no longer needed, otherwise the final portion of the stored data will not be dumped to the disk; additionally, events will be fired on a null object – mayhem.<br>
-	***Managing input blocks.*** Each Block is initialised by a method called <code>ConfigureInputs()</code> – the reason this method is separated from the constructor lies in the necessity of allowing for loops in the block graph. As a result, a list called <code>InputBlocks</code> is built, which contains the blocks this block can get input from; still, remember that this does not necessarily mean that the block has subscribed to all of its input blocks: as already explained, (un)subscribing to/from one’s input blocks boils down to (un)subscribing to/from the input block’s output event handler and allows for dynamic management of input handling. In fact, blocks have a method to check whether block A has B among its inputs, and another one to see whether A is currently subscribed to B: <code>HasInput</code> and <code>IsSubscribedTo</code>. In the YAML configuration file a - (dash or minus symbol) in front of a block’s name in the list of inputs means that this block is an input block, but we don’t subscribe to it upfront.<br>
-	***Sending out stuff.*** The <code>Output</code> event handler is fired by the <code>SendOutput(value)</code> method. Two important details here:
    -	Firing an event means to call a list of functions (the call-backs which have subscribed to this event), and these functions can be called either synchronously or asynchronously, depending on whether the execution must wait for the computation to return or not; this is regulated using the <code>syncSendOutput</code> flag. By default, and in the vast majority of cases, the event must fire its call-backs asynchronously in order not to wait for all output processing to happen, which would de facto stop everything till the last block in a chain has finished processing its own stuff; but there are cases in which the temporal sequence of the event must be respected by all means, e.g., when dealing with a stream to be parsed; in that case, you must set the syncSendOutput flag to true.
    -	Here is also where we set the IsStumbling flag: stumbling happens whenever the previous SendOutput is still executing while a new instance of it is being called upon (remember: everything is asynchronous and multi-threaded here!). We use locking on an object called <code>StumblingLock</code> to check for this and prevent clogging the stack: if the block is stumbling, we absolutely do not execute the loop.<br>
Of course, there are blocks which do not produce any output (e.g., Buffer) so they will never call <code>SendOutput</code>.
-	***Receiving stuff.*** <code>OnNewInput</code> is the only abstract method in a Block and therefore it is what makes the class abstract. Notice that it is, too, protected by a lock – you don’t want to react to a new input while another one is being processed, which would immediately lead to data unsafety. Here, too, notice that there are blocks which do not receive any input whatsoever, e.g., <code>ScheduledTimer</code>, in which case <code>OnNewInput</code> can be called in principle, but this should produce a warning or, in the worst case, throw an exception.
-	***The Control Panel.*** Each block has an associated <code>ControlPanel</code> (cp) which is an abstract class inheriting from <code>Form</code>. Use the cp to access at runtime all parameters related to the block, as well as to visualise the data going through it. Each cp can be shown or hidden through the block by invoking <code>ShowHideCp</code> and you can program your own actions to be performed when the block gets left- or right-clicked in the block table (<code>MouseLeftClick</code> and <code>MouseRightClick</code>).<br>


#### Blocks.Dict
All blocks are supposed to be referenced in the static dictionary <code>Blocks.Dict</code>. Adding a block to it must be performed separately, soon after creating the block; so far this only happens in the Parser. If you create your own block outside the parser / after the parsing phase, *do not forget to add it to the dictionary*.

#### CfgParser
The Parser reads in a configuration file written in YAML, creates the blocks declared in it and aptly populates <code>Blocks.Dict</code>. It heavily relies on <code>YamlDotNet</code>, a library which does exactly that, parsing YAML into something, so the process of parsing itself (“deserialization”) is of no interest here. Here’s just a couple more details you might be interested in.

First, the Parser uses an intermediate structure, <code>CfgBlock</code>, which stores the elements read off the cfg file. Each element in the cfg file must correspond by *name* to a field in the structure, e.g., if the string <code>“Type: ScheduledTimer“</code> is found in the cfg file, then after deserialization the string field <code>CfgBlock.Type</code> will contain the string “ScheduledTimer”. So far, the cfg file can only contain block definitions; further syntactic possibilities will be added as needed. Meanwhile you might want to get familiar with the YAML syntax – there is an <a href="https://www.yaml.in/">official website</a> for that.

Second, how can the Parser create the blocks, since new types of blocks, *unknown at compile time*, can appear in the cfg file? We used to have a very large switch clause, which needed to be updated manually each time we wanted to have a new type of block; then I discovered the C# *reflection*, which allows to build new types and instantiate them at runtime. Look at this marvellous piece of code:

```cpp
Type thisBlockType = typeof(Block).Assembly.GetType("iM." + cfgbEntry.Value.Type);
object thisBlockInstance = Activator.CreateInstance(thisBlockType, new object[] {

    cfgbEntry.Key,
    cfgbEntry.Value.DesiredRate,
    cfgbEntry.Value.Inputs,
    cfgbEntry.Value.Params,
    cfgbEntry.Value.Path

});
```

Given the type of the block as a string, we first literally create its type <code>thisBlockType</code>, then we instantiate it with <code>Activator.CreateInstance</code>, using the parameters found in the cfg file. Absolutely beautiful. The only drawback is that every block constructor must adhere to this signature, and that is another reason why there is a further method <code>ConfigureInputs()</code> in each block, in which consistency checks on the inputs and parameters are performed.

This file contains basic definitions of machine learning classes, which are *not* blocks; rather they must be embedded into blocks to perform ML operations such as, e.g., model building, updating and downdating, predicting, and calculating a confidence interval for the prediction. ## The Block Table, Control Panels and Monitors (Visualisation/)

#### The Block Table
There is not much the <code>BlockTable</code> class, based upon the packages <code>GraphX</code> and <code>QuickGraph</code>, does: essentially, it first creates a graph out of <code>Blocks.Dict</code>, then it passes on the graph to a new instance of a XAML window called <code>BlockTable_window</code>, that is, the block table itself, where the graph visualisation happens. The engine behind the <code>BlockTable_window</code> draws and decorates the graph – that is what the constructor of the class does. Even more importantly, it can associate call-backs to interaction events related to single vertices of the graph, which in turn correspond to the blocks in <code>Blocks.Dict</code>. This means that you can program what will happen when the user left- or right-clicks on a block or drags it around and then drops it, etc. This gives us endless possibilities to enhance the displaying of the data flow in iM. As we have already seen, there are virtual functions in a Block for defining what mouse-clicking on the block does. By default, left-mouse-clicking shows/hides the block’s cp.

#### Control Panels
A <code>ControlPanel</code> is a simple class with a virtual method, inheriting from <code>Form</code>, which does little more than some bookkeeping and attaching/detaching its own (virtual) <code>cpRefresh()</code> routine to the <code>dtmRefresh</code> timer, *only as long as it is shown* (uses the <code>VisibleChanged</code> event to this aim). This way we guarantee that no CPU time is wasted trying to refresh something which is not displayed! Here we also define that pressing ESC on a cp hides it.

#### Monitors
A <code>Monitor</code> is, as well, a simple class with a virtual method, this time inheriting from <code>UserControl</code>. It really does nothing but creating a Mathnet <code>Vector</code> to hold the “signal” to be displayed, which must happen in the virtual method called <code>Update()</code>. If you then look at the real Monitors, e.g., <code>SpiderPlotMonitor</code>, you see that it overrides the <code>Update()</code> method and it does over there all signal updating. All Monitors must behave like this: for instance, whenever using a Monitor in a cp, *do not* place a timer in a Monitor for refreshing – refreshing is taken care by placing the <code>Update()</code> method within the <code>cpRefresh()</code> method of the cp, this way letting the global dtmRefresh timer take care of everything.

#### SimpleProgressBar
Additionally, an example of a new UserControl you can use in your Monitors – a progress bar which does *not* use any annoying animation, and can be either horizontal or vertical.

## Building your own Blocks

The definition of a specific block, found in the related <code>.cs</code> file, consists of a concrete class inheriting from <code>Block</code>, plus its cp. Each file should be related to one block type only, and should contain:
-	The definition of the block’s cp:
```cpp
    public partial class cp<Type> : ControlPanel {...}
```
-	The definition of the block type itself, as a concrete instance of the class <code>Block</code>:
```cpp
    public class <Type> : Block {...}
```

Please keep this structure as much as you can and take inspiration from existing examples when you build you own new Blocks. 

>[!Take Home Lesson]
>Keep in mind what the intended semantics of a block is, and accordingly split/group the task(s) you need to implement. For instance, if you need to extract novel features from the EMG signal, it is probably OK to enforce this functionality in a single Block. On the other hand, would it make sense to have this Block also send the features off to a new device, e.g., through a UDP channel? The answer is: definitely not. For this, you would need another Block, possibly chosen among the ones already present in iM, which would be connected in a cascade after this one. *Modularity* is the keyword here.

## The Control Panel
The cp must be filled with buttons, gauges, labels, and monitors (time plots, spider plots, etc.) apt for checking the status of, and controlling, your own Block, and visualising the data going through it. Notice that some blocks might define no cp: in that case nothing will happen when the user clicks on the Block in the block table. But as a standard, *there should be a cp*, maybe even just to visualise what’s flowing through the Block. No cp means that there is no way of controlling / inspecting the cp at runtime. Be liberal with this: a cp will waste no CPU time unless it it necessary, so it does not hurt to have one!

All cps must inherit from the abstract class <code>ControlPanel</code>, which in turn inherits from the Windows Form. You can and should use the Visual Studio designer to design your own cp. Once this is clear, there are only three things a cp must do: declare and assign the <code>_SourceBlock</code>, that is the block it refers to, have a constructor in which some basic bookkeeping is done, and override the virtual method called <code>cpRefresh</code>, which takes care of refreshing the cp itself. Consider an existing cp, that of the Filter block:

```cpp
Filter _SourceBlock;
public cpFilter(Filter _SourceBlock) : base(_SourceBlock) {
   InitializeComponent(); this._SourceBlock = _SourceBlock;
}
override protected void cpRefresh(object o, EventArgs e) {
   smFilter.Update(_SourceBlock.Data as Vector);
}
```

That is all, folks: in <code>cpRefresh()</code> we just <code>Update()</code> the <code>ScopeMonitor</code> called <code>smFilter</code> using the data found in the source block. More complex examples can be found in other cps such as, e.g., that of an <code>IncrementalPredictor</code>, where also the behaviour of some buttons must be defined – check it out.

A remarkable point here is the following: *there should be no updating of the cp outside <code>cpRefresh()</code>*, since that method is optimised in the base class <code>ControlPanel</code>. In particular, acting on buttons should change public status flags in the block, then you should read off those status flags and accordingly refresh the cp in <code>cpRefresh()</code>. The reason for this is that the status flags might change for some other reason, too, other than being clicked in the cp, so the refreshing must happen in one place only, in order to guarantee coherence of the interface. My favourite example of this philosophy is the <code>ScheduledTimer</code>, which has a button to start and stop the timer and it should change its own Text according to whether the timer is running or not (“stop” while it is running and vice-versa). Now, check this out: the text is not changed when the button is pressed (that is, in <code>cbStartStop_CheckedChanged()</code>), but rather in <code>cpRefresh()</code> according to the value of a flag called <code>IsRunning</code>, which is taken care of in the base abstract class called <code>Timer</code>:

```cpp
override protected void cpRefresh(object o, EventArgs e) {
    cbStartStop.Text = _SourceBlock.IsRunning ? "Stop" : "Start";
}
void cbStartStop_CheckedChanged(object sender, EventArgs e) {
    if (!_SourceBlock.IsRunning) _SourceBlock.Start(); else _SourceBlock.Stop(); 
}

```

This way, *operating on the block* and *showing the block’s status* are completely separated from each other, and no matter who acts on the <code>IsRunning</code> flag, the button will always display the correct text.

### The Block

Any concrete block type must:
-	Have a fixed constructor, see, e.g., the definition of the ScheduledTimer again.
-	Override the method <code>ConfigureInputs()</code>, which must contain a call to the base method at the beginning and the creation of the cp at the end:
    ```cpp
    override public void ConfigureInputs() {
    base.ConfigureInputs();
    […]s
                cp = new cpScheduledTimer(this);
    }
    ```
Between these calls, still within <code>ConfigureInputs()</code>, a block should check for coherence of the input blocks and parameters; for instance, a <code>ScheduledTimer</code> must have no inputs; a <code>DesiredRate</code> must always be positive; and so on.
-	Finally, you need to override the abstract method <code>OnNewInput()</code>, taking care of inputs. What happens when this block receives an input? Who is the sender, and what is the type of datum received? Notice that this is an abstract method, so even if your block is not supposed to receive any inputs, it must be defined.

All the rest is taken care of in the basic class <code>Block</code>.

### Timers
Let us first talk about timers – timers are the prime movers of iM, which make everything else move in the blocks’ world. There are three files under <code>Timers/</code>.

#### Timer
Timers are, well, timers, like the ones you find in Windows, but better: they fire events at regular rates. The basic abstract class <code>Timer</code> just contains <code>Start()</code> and <code>Stop()</code> methods which set the <code>IsRunning</code> flag and a predefined <code>Fire()</code> method which just sends out empty events thanks to <code>SendOutput(null)</code>. A concrete timer will only need to determine how <code>SendOutput</code> is called. Notice that in this basic class we also state that right-clicking on a Timer will start/stop it.

#### ScheduledTimer 
A <code>ScheduledTimer</code> adds to / removes from the <code>Scheduler</code> its own Fire upon starting and stopping – nothing else, really. It must have no inputs and no parameters. Its cp only allows for starting and stopping.

#### DecimatorTimer
A <code>DecimatorTimer</code> receives input events from a <code>Timer</code> but only lets some of them go through, thus effectively *decimating* what it receives. This is done using an integer counter and the remainder function. This kind of timer will buy you a timer without putting a new function on the Scheduler’s shoulders, which is a very expensive matter. Notice that starting and stopping a <code>DecimatorTimer</code> boils down to un/subscribing from/to its input timer!

>[!NOTE]
>Why having an abstract class Timer and not simply a new class for each timer-like block? I can see at least three reasons why:
>1.	Timers have functionalities in common (otherwise they wouldn’t be timers!) and it is a good programming practice to define and implement all these common functionalities in a basic class, to avoid duplicating code and fully benefit of any further optimisation and bugfix.
>2.	Some blocks need a timer as input (SinGenerators, see below), but it is irrelevant how this timer is implemented. So in a SinGenerator’s ConfigureInputs()we can force that its one an only input must be a Timer, no matter whether a ScheduledTimer or a DecimatorTimer, or any other kind of timer.
>3.	Suppose you have a new kind of timer, for instance, say, an ExternalTimer whose pace is given by an external hardware clock: building a new instance of Timer for it, instead of a completely new class, immediately buys you the common functionalities and compatibility with all existing blocks for free.
>Think of this, when designing your own new blocks: can they perhaps be grouped and made to inherit from an abstract block class? Think the semantics of your blocks, ***before starting to implement***!

### Devices
I group under “devices” the blocks which take care of devices such as, e.g., sensors, robots, VR artifacts, etc. As a matter of fact, a device block should be injecting stuff in the system (from an input device such as a myo) or outputting stuff out of the system (to an output device such as a Blender arm model).


#### SinGenerator
A <code>SinGenerator</code> generates a $$d$$-dimensional synthetic sinusoidal signal, extremely useful if you need to test your blocks but have no real signal reading device available. It just evaluates and sends the signal each time it receives an event from a <code>Timer</code>, and it must be constructed using one input block only, and indeed a <code>Timer</code>. Its <code>DesiredRate</code> is the input timer’s desired rate. Its parameters, read off the cfg file, define the amplitude, frequency, and phase of the sinusoidal signals. Check out how this is implemented and then written in the cfg file.

#### Myo
A myo behaves exactly like a <code>SinGenerator</code>, but instead of generating signals, it obtains exactly eight of them from the myo by interacting with it via the BLE stack. This block uses a series of specific helper functions for BLE, not incidentally to be found in <code>BluetoothLEManager.cs</code>, which can be used for any other BLE device. Due to the need to give the user the chance to scan the BLE stack and choose a specific device (unless a MAC address appears in the cfg file), the cp to this block is rather complicated; as opposed to this, thanks to the functions available in <code>BluetoothLEManager.cs</code>, the block itself is easy to read.

#### Stimulus
A stimulus is, in general, in our framework, something you do to “stimulate” a response from the participant. It can be a voice command, something happening in VR, a set of written instructions; or, in the simplest case, a visual stimulus on the screen. The <code>Stimulus</code> block enforces a simple Finite State Machine and takes a set of “actions” as input in the cfg file; then, it sends out target values representing the sequence of actions in a precisely timed fashion. For instance, from a *rest* arm/wrist/hand configuration, the Stimulus can produce the target values representing a smooth transition to a *power grasp* configuration. The idea is that of displaying this sequence on a 3D model, for instance the white Blender arm, and ask the participant to repeat those movements as closely as possible. This is why, in the end, the main Blender model we use displays *two* arms instead of one: the white one, on the left-hand side, is supposed to show a visual stimulus; the skin-textured one, on the right, should show the configuration predicted by our myocontrol system. The stimulus can be either used to gather data in a structured fashion, or to assess the performance of a ML model by enforcing the so-called TAC (Target Achievement Control) test. The output of a Stimulus is a pair (state, target value) where “state” is the name of the current state and target value is the target value being generated at this very instant of time.
Whereas the SinGenerator, the Stimulus and the Myo are “input” devices, injecting signals into the system, here is an “output” device, receiving activation values signals and using them to control the Blender arm models.

#### Blender Arm
This block receives target values as 12-dimensional vectors, then packs them into 9-dimensional ones in order to comply with the protocol required by the Blender models, and lastly it sends them off to a UDP client; in the cfg file, the host and port number of the UDP client can be set. That’s all, folks.

### FlowControl
Here’s a set of blocks which “control the flow” of data, i.e., they switch from block to block, select specific parts of their input, and send out discrete (sporadic) commands.

#### Buffer
A <code>Buffer</code> is supposed to occasionally (upon being instructed to do so by a Trigger) subscribe to a data provider, collect data from it, unsubscribe from it, then store the collected data in a list of pairs (target value, data cluster) called <code>dB</code>. As you can imagine, this is the building block to enforce batch machine learning in iM: after the data collection is finished, a <code>BatchPredictor</code> will query the dB and use the collected data to build a model and start predicting values according to signals arriving from a data provider. Notice that the Buffer’s cp not only (roughly) shows at run-time what <code>dB</code> contains, but it also allows you to clear or save it.

Notice that here we face a dilemma: just *how* is the BatchPredictor supposed to obtain the <code>dB</code> from the Buffer? If the blocks’ world were perfect, then all blocks would be isolated classes enforcing no public methods, and all input/output would occur via the SendOutput / OnNewInput mechanism; but in our case, this seems an overshoot: essentially all blocks would need be connected to all others! The BatchPredictor/Buffer interaction is a good example: the BatchPredictor should send a “sendDB” command to the Buffer, which would respond by sending the dB off to the predictor. It is definitely simpler to have the Buffer expose dB as a public field that any block can query. Although this is less elegant than it could be, I believe it makes things quite easier. As a matter of fact, notice (see below) that a BatchPredictor has a Buffer specified among its parameters in the cfg file, and not among its inputs, since it will never really receive any input from the Buffer; but it needs to somehow know which block is the Buffer providing the data to build its own model.

Furthermore, let us a have a closer look at the block’s definition, actually demonstrating the power of iM’s run-time block un/subscription system. On receiving an input within <code>OnNewInput</code>, Buffer first tells whether it comes from the data provider or from the trigger, then it further differentiates the action to be taken based upon the value it has received:

```cpp
if (sender == InputTrigger)
    switch (value)
        case null: UnsubscribeFrom(InputDataProvider);
        default: SubscribeTo(InputDataProvider);
else if (sender == InputDataProvider)
    dataCluster = dataCluster.Stack((value as Vector).ToRowMatrix());
```

If the sender is the trigger, then the Buffer starts/stops collecting data (it stops if the received value is a null), by un/subscribing from/to the data provider; if the sender is the data provider, it just stores the received data in a temporary matrix. There are more details of course, please look at the code and try to understand it. Notice that, if we did not un/subscribe from/to the data provider on demand, <code>OnNewInput</code> would be called as often as the data provider would fire no matter whether the buffer was interested in storing the data or not. This way instead, we spare <code>OnNewInput</code> from being called many useless times.

#### Trigger
In general, a <code>Trigger</code> block is supposed to sporadically send out stuff to other blocks, in a format which depends on the destination block – notice the extremely terse code in the definition of the block, which resorts to one public method

```cpp
public void Send(object o) { SendOutput(o); }
```

In the cfg file though, you can specify a list of (string, target value) pairs, meaning a name and an action, and the Trigger’s cp takes care of building up the protocol which will then be accepted, e.g., by a Buffer: pressing the left or right arrow key on your keyboard cycles through the actions specified in the cfg file, whereas keeping the down arrow key pressed sends out the target value (action) associated to the current name. Releasing the down arrow key sends out a null – again, check out that the Buffer “understands” this communication protocol.


#### StimTrigger
A <code>StimTrigger</code> is a “converter” from stimuli values to trigger commands, apt to control a Buffer. In practice it sends off the Stimulus’ target value only as long as the Stimulus remains in the capture state; on exiting from that state, it sends off a single null value. 

#### Switch
A Switch receives input from two block and, upon clicking the Switch button in its cp or being right-clicked, switches the output from input block 1 to input block.

#### Selector
A Selector is supposed to receive tuples as inputs, and literally selects one element of the tuple. So far it is just a hack, only used to take a Stimulus’ output and trim away the name of the state, leaving the target values as input for a Blender arm controller.

### Learning
Blocks in this directory are supposed to enforce machine learning, i.e., to provide data to and collect predictions from the classes found in <code>Learning.cs</code>. For instance, Ridge Regression need to gain access to a data set and target values in order to build a model; then, it needs to be fed input values (EMG, for instance) to provide a prediction. This is what these blocks enforce.

#### BatchPredictor
Second type of machine learning block: this one needs no Buffer, rather a Trigger that will, occasionally, provide target values. Check out the IncrementalPredictor’s <code>OnNewInput</code> method: on receiving from the Trigger (called <code>TargetProvider</code> in this case!) it stores the target value it just received, assuming that the samples it is receiving right now must be associated to this target value; and in fact, upon receiving stuff from the <code>SampleProvider</code>, if the target value is not null, that is, if an association is being made, it updates its own model. Regardless of this, it also sends out a prediction.

#### TAC
Finally, a Target Achievement Control block in our setting is nothing but a block which receives target values from two blocks and compares them: if they remain similar to each other for a specified amount of time, then the task is successful. Usually, the two input blocks to a TAC will be a Stimulus, providing the configuration the participant is supposed to reach, and a Batch- or IncrementalPredictor, providing the configuration the participant is currently producing. Notice the convenience to act directly on the Stimulus block in order to kick it out of the “capture” state if the task has been achieved. Here, too, as it was for the BatchPredictor, a Stimulus block is among the parameters of the TAC.

### Other Blocks

#### Function
A block which can be literally “programmed” in the cfg file to operate on its inputs via a component-wise mathematical function. Uses a switch clause in <code>ConfigureInputs()</code> to literally build the function as a λ-expression; the function is then applied to all component of the block’s input vector as soon as it is received.

#### Filter 
A very simple digital IIR (FIR if $$d_0=1$$) filter implementation: reads in the numerator $$[n_0,…,n_P]$$ and denominator $$[d_0,…,d_Q]$$ of the filter out of the first and second parameter in the cfg file then uses a matrix as a “buffer” to compute the formula

$$y[n]= ∑_0^P[n_i x[n-i]]-∑_0^Q[d_i y[n-i]]$$

for the filtered value and sends it out. So far, the numerator and denominator coefficients must be specified in the cfg file, so Matlab or any other mathematical tool comes in handy here. There are examples of Matlab code in the cfg files.

#### Resampler
Extremely simple block which sends out a value read from a data provider *only when it receives an event from an input timer*, effectively up- or downsampling a signal. Be careful here, subsampling without first adequate filtering can lead to aliasing.
